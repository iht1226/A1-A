# 0.4.0 움직임 수집 신뢰성과 실기기 검증

## 제공된 첫 실사용 기록의 해석

사용자가 제공한 2026-11-18 기록은 01:23 예약, 08:00 FINAL 요청과 실제 소리·진동 정상, ADAPTIVE_020, 움직임 95구간, 심박 2,443포인트입니다. 개발 환경에서 해당 기기를 직접 관측한 기록은 아닙니다.

45분은 2,700초이며 5초 구간은 약 540개가 필요합니다. 95개를 모두 완전한 구간으로 가정해도 475초, 약 **17.6%가 상한**입니다. 실제 coveredMillis가 5초 미만이면 더 낮습니다. 구간 위치와 원시 이벤트가 없으므로 어느 시간대가 비었는지나 단일 원인을 역으로 확정할 수 없습니다.

심박 포인트 수는 CPU가 그만큼 깨어 있었다는 증거가 아닙니다. Health Services는 여러 시각의 포인트를 배치 전달할 수 있습니다. 기존 적응형 추정기는 움직임 기준선 관문에서 반환하면 심박 근거를 계산하지 않으며, 화면의 심박 신뢰도 0은 미평가인 경우도 있습니다. 0.4.0은 실제 심박 등록 상태·포인트 수·기기 품질별 유효 수를 별도 진단합니다.

## 코드에서 확인한 사실과 남은 가설

| 예약→실행 | sensorStart를 exact-and-allow-while-idle로 예약하나 실제 시작 시각 미기록 | 예정 시각, 실제 서비스 명령/수집 시작/등록, 시작 지연, 마지막 저장, 알려진 종료와 종료 미확인을 구분 |

버킷 경계의 약 4% 손실만으로 전체 17.6% 상한을 설명할 수는 없습니다. 따라서 이 버그 수정 하나가 실사용 원인을 해결했다고 해석하지 않습니다.

**아직 가설인 것:** Watch7의 실제 wake-up 가속도 존재/선택 결과, 공유 FIFO 초과, non-wake-up의 AP suspend 중 덮어쓰기, OEM의 서비스 종료/권한 제한, 정확도 0 비율, SQLite 저장 지연이 해당 95구간의 지배적 원인이었는지입니다. 원래 기록만으로 입증하지 않습니다.

## 화면 꺼짐과 배터리의 한계

[공식 SensorManager](https://developer.android.com/reference/android/hardware/SensorManager)와 [AOSP FIFO/suspend 설명](https://source.android.com/docs/core/interaction/sensors/batching)에 따르면 non-wake-up 센서는 AP가 suspend 중일 때 앱에 이벤트를 전달하도록 CPU를 깨우지 않습니다. 이때 maxReportLatency를 짧게 지정해도 suspend 중 전달을 강제하지 못하고 FIFO가 넘치면 오래된 이벤트가 사라질 수 있습니다. Foreground Service는 프로세스 우선순위와 실행 자격을 제공하지만 지속적인 CPU 깨움을 뜻하지 않습니다.

| 방식 | 신뢰성과 비용 |
|---|---|
| wake-up 가속도 + 5Hz/최대 5초 배치 (우선) | 하드웨어가 배치/용량에 따라 AP를 깨울 수 있음. 앱의 지속 WakeLock 없음. 10초 배치보다 기상 빈도가 늘 수 있어 실제 배터리 비교 필요 |
| non-wake-up FIFO (허용되는 대체) | 연속성을 보장할 수 없음. 지연 데이터를 보존해도 이미 덮어쓴 FIFO는 복원할 수 없음. 부족하면 조기 판단 보류 |
| FIFO 없는 wake-up | 이벤트별 AP 기상이 발생할 수 있음. 진단에 표시하며 실제 소비를 확인해야 함 |
| 측정 구간 전체 PARTIAL_WAKE_LOCK | non-wake-up 전달에는 도움이 될 수 있으나 CPU 유지 비용이 있음. 요청한 배터리 원칙 때문에 구현하지 않음 |
| 저주파/짧은 관측 버스트 | 버퍼 지속시간·소비와 움직임 해상도의 교환. 현재 80% 관측 관문을 만족하지 못하면 버스트를 연속 관측으로 간주할 수 없음. 별도 실측 없이 대체하지 않음 |

Health Services의 심박/걸음 포인트가 원시 XYZ 가속도와 같다고 가정하지 않습니다. 운동 세션이나 비공개 삼성 API로 우회하지 않습니다. 강제 중지·방전·전원 꺼짐·권한 철회·OEM 정책은 앱이 해제할 수 없습니다. 재부팅 후 최초 잠금 해제 전에는 원시 센서 DB를 사용할 수 없지만 기존 direct-boot 정시 예약은 분리되어 있습니다.

## 진단 사용

워치 설정의 **센서 진단 · 화면 꺼짐 시험**, 휴대전화 상단 **센서 진단**, 또는 각 기상 이력의 진단 버튼을 엽니다.

- 예열/판단 각각의 이벤트 시간 관측률, 저장된 유효 구간 관측률, 관측 초/분모, 최대 연속 미관측 시간.
- 분 단위 관측률, 전체 관측률, 실제 수신 공백과 최대 지연, 60초 넘게 지연되었지만 보존한 이벤트 수.
- 실제 서비스/등록/종료 시각, 센서 이름·vendor·version·전력 힌트·wake-up·FIFO·요청 주기/배치.
- 총 콜백/채택/정확도 상태/폐기 사유별 수, 유효 저장 구간, 중복, DB 오류/쓰기 최대 지연과 분석 최대 시간.
- 재시작 generation, 재등록·flush 요청/완료, 전원 상태 스냅샷, 심박 등록·수신·기기 품질, 마지막 보류 이유.

전원 상태는 코드가 실행되는 틱의 스냅샷입니다. AP가 자는 동안의 상태 변화 전체를 추적하거나 Doze 원인을 확정하는 OS 트레이스가 아닙니다. 하드웨어 전력(mA)은 센서 descriptor 힌트이며 앱 전체 배터리 측정값이 아닙니다.

프로세스가 onDestroy 없이 사라지면 종료 시각을 만들어내지 않습니다. 마지막 저장과 종료 미확인을 표시하고, 예정 시간의 관측되지 않은 꼬리를 공백으로 계산합니다. 실제 첫 알람 요청이 있으면 그때 관측 비교를 잘라 이후 데이터를 가정하지 않습니다. 원시 시간 범위 상세는 최대 4,096개로 제한하며 초과 시 보수적 하한임을 표시합니다.

원본 가속도 이벤트의 측정 시각(nanos/epoch), 실제 수신 시각, 에너지, 정확도, 폐기 사유는 워치 SQLite audit에 배치 저장합니다. 분석에 사용한 5초 구간에도 가용해진 수신 시각을 저장합니다. 원본/심박/구간은 다음 수집 때 48시간 이전을 정리합니다. 상세 진단은 최근 20세션, 사건은 세션당 최근 300건입니다. 데이터가 사라지거나 저장이 실패하면 이를 정상 관측으로 가정하지 않습니다.

진단은 일반 보고서의 클라우드 동기화 필드에 추가하지 않습니다. 휴대전화로 가져오기/워치에서 보내기는 **사용자가 요청한 nearby 노드의 MessageClient**만 사용합니다. 원시 이벤트·개인 기준선은 전송하지 않습니다. 외부 진단 서버와 자동 업로드는 없습니다. 화면의 **진단 텍스트 공유**로 로컬 보고서를 내보낼 수 있으며 공유 화면이 없는 워치는 클립보드로 대체합니다.

## 수면 없이 하는 10~15분 시험

1. 워치에서 움직임 측정 권한을 확인합니다. 심박은 선택 사항입니다. 충전 여부·시작 배터리·절전 모드를 따로 기록하세요.
2. 가까운 알람/실제 기상 수집과 겹치지 않는 시간을 고릅니다. 수집 중 또는 기상 측정 시작이 16분 이내이면 시험을 거부합니다.
3. **10분** 또는 **15분 수집 시험**을 시작하고 새 보고서의 실제 시작과 센서 등록 결과를 확인합니다. 첫 5분을 예열, 나머지를 관측 판단 구간 형식으로 구분하지만 시험에서는 조기 알람을 실행하거나 수면 단계를 판단하지 않습니다.
4. 워치를 착용하고 화면을 끕니다. 2~3분은 가만히, 중간에 몇 차례 손목을 움직이고, 나머지는 가만히 둡니다. 화면을 계속 켜서 실패를 숨기지 마세요.
5. 종료 후 보고서를 확인합니다. non-wake-up에서 AP가 잠들면 종료 처리도 다음 CPU 실행 때 늦어질 수 있습니다. 실제 종료와 예정 종료를 구분하며, 측정 시간은 예정 범위 밖으로 늘리지 않습니다.
6. 휴대전화와 근처 연결에서 진단을 가져와 텍스트로 보관합니다. 같은 조건에서 화면 켬/꺼짐, 일반/절전 상태를 각각 반복합니다.

**공학적 수집 검증 목표:** 10분은 약 120구간/600초, 15분은 약 180구간/900초가 목표이며 처음/마지막 부분 구간은 차이가 있습니다. 실제 이벤트 수는 주기 힌트와 다를 수 있습니다. 이벤트/저장 시간 관측률 95% 이상, 최대 공백 15초 이내를 우선 목표로 비교하세요. 이는 기상 알고리즘의 관문을 바꾸거나 임상적 타당성을 주장하는 기준이 아닙니다. 가만히 있어도 유효한 시간은 관측으로 집계되어야 하며, 0에 가까운 움직임을 누락으로 처리하지 않습니다.

기존 알람 설정·계획·기상 이력에는 시험 계획을 저장하지 않습니다. 시험 원본과 진단 ID만 별도로 만듭니다. 시험을 중단해도 일반 알람 예약은 취소하지 않습니다. 실제 알람 측정이 도래하면 시험보다 우선합니다.

## 다음 실제 밤의 확인 절차

08:00/스마트 30분이면 예정 센서 시작 **07:15**, 판단 시작 **07:30**입니다.

1. 기존 예약·08:00 FINAL이 유지되는지 확인하고 0.4.0의 실제 버전 코드와 센서 종류를 기록합니다.
2. 다음 날 실제 시작이 07:15에서 얼마나 지연됐는지, wake-up인지, FIFO/배치가 무엇인지 먼저 확인합니다.
3. 예열 07:15~07:30과 판단 07:30~실제 관측 종료 각각의 이벤트/저장 관측률과 최장 공백을 봅니다. 정시까지 관측했다면 약 540구간·2,700초가 전체 상한입니다. 조기에 실제 알람을 요청했다면 그 이전까지만 비교합니다.
4. 95구간과 단순 개수만 비교하지 말고 **유효 관측시간/예정시간**, 분 단위 누락 위치, 최대 수신 지연·실측 공백, 폐기 사유, 서비스 재시작·DB 오류를 비교합니다.
5. 이벤트 수신 자체가 적고 non-wake-up이면 AP/FIFO 제한을 우선 의심합니다. 수신은 많고 UNRELIABLE이 많으면 정확도 상태가 원인일 수 있습니다. 채택은 많고 저장이 적으면 쓰기 오류/지연·중복을 봅니다. 서비스 실제 시작이 늦으면 시작 권한·예약 전달과 OS 로그를 확인합니다.
6. 충분한 관측인데 기상 조건 미달이면 정상적인 보류입니다. 두 알고리즘에 조기 제안이 반드시 생겨야 하는 시험이 아닙니다. 심박만 많다고 강제로 조기 알람을 울리지 않습니다.
7. 배터리는 같은 사용 조건과 측정 구간 길이에서 여러 밤 비교하세요. 이번 변경으로 배터리 소비가 줄었다고 주장하지 않습니다. 정시 소리·진동·해제·다시 알림도 다시 확인하세요.

**95구간 문제가 실제로 개선됐다는 결론은 아직 낼 수 없습니다.** 새 버전의 화면 꺼짐/실제 밤 로그가 필요합니다. 본 버전은 관측 누락을 줄이는 구현과 실패 위치를 식별할 도구를 제공합니다.

## 저장 입력 오프라인 리플레이

워치에서 수집이 끝난 일반 기상 진단을 선택하고 **오프라인 리플레이**를 누릅니다. 저장된 파라미터·개인 기준선·실제 wall/elapsed 평가 시각·서비스 generation·당시 심박 사용 가능 여부·정확한 입력 ID 목록을 사용합니다. 측정/수신이 해당 평가 시각을 넘는 입력은 포함하지 않습니다. 재시작 시 지속 확인 관문을 새로 시작했던 것도 재현합니다.

기존 0.1.1과 ADAPTIVE_020의 제안 시각·이유·근거 지수 일치 여부를 표시합니다. 원본이 보관 기간을 지났거나 파라미터 버전이 다르거나 실제 평가 기록이 없는 독립 수집 시험/이전 버전이면 정확한 리플레이가 불가능하다고 표시합니다. 알람을 다시 울리거나 실제 기상 이득을 증명하는 시험이 아닙니다.

## 자동 검증의 범위

기존 알람·알고리즘·업데이트 회귀 시험을 유지합니다. 추가 시험은 버킷 경계 적분, 불규칙 간격·장시간 공백, 늦은 배치, 미래/중복/역순/오류 이벤트, FIFO 정책, 실제 입력 목록 리플레이, DB v2→v3·최초 수신 보존·원시 감사, 시험 권한 거부/예약 보호, 모의 센서 재등록과 재개, 종료 미확인 공백, 전송용 개인정보 제외를 포함합니다.

Robolectric의 화면 꺼짐 상태와 수동 SensorEvent 주입은 Watch7 하드웨어 전달, 실제 Doze/프로세스 종료/재부팅 정책, 삼성 센서 정확도나 배터리를 검증하지 않습니다. 수면 효과에 대한 데이터도 아직 없습니다.

## 고정 서명 배포 보호

기존 apk-build1006의 APK 검증 로그에서 확인한 **공개 인증서 SHA-256**을 gradle/release-signing.sha256에 고정했습니다. 개인 키나 암호가 아닙니다. 새 APK 두 개의 인증서가 이 값과 일치하지 않으면 update.json 생성과 Release 배포를 중단합니다. GitHub Secrets와 개인 키는 읽어 내보내거나 변경·재생성하지 않습니다. 서명 정책의 통과/혼합 키/잘못된 pin은 Python 자동 테스트로 검사합니다.
