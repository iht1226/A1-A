# 0.5.0 화면 꺼짐 움직임 수집 시험

Watch7에서 사용자가 제공한 두 시험 모두 STM LSM6DSV 가속도 센서를 사용했습니다. 이 센서는 non-wake-up이며 FIFO max/reserved는 300/300, 샘플링 요청은 200,000µs, 배치 요청은 5,000,000µs였습니다. 두 시험에서 센서 등록이 성공했고 DB 오류와 서비스 재시작은 없었습니다.

| 10분 시험 | 움직임 관측률 | 저장 구간 | 관측 시간 | 최대 공백 | 이벤트 | 심박 |
|---|---:|---:|---:|---:|---:|---:|
| 화면 대부분 꺼짐 | 14.4% | 37 | 약 85초 | 143초 | 993 | 51 |
| 화면 대부분 켜짐 | 98.3% | 120 | 588초 | 1초 | 9,409 | 424 |

두 번째 시험에서 화면이 꺼진 구간은 마지막 약 31초였습니다. 98.3%는 시험 전체 관측률입니다. 센서 콜백 수는 드라이버와 Android가 실제 전달한 결과이므로 샘플링 요청값으로 손실 건수를 정확히 역산할 수 없습니다. 보고서는 측정 시각 사이 실제 미관측 시간과 최대 공백을 비교합니다.

## 원인과 시험 설계

0.4.0은 foreground service에서 센서를 등록했지만 수집 서비스의 CPU 유지 요청은 없었습니다. non-wake-up 센서는 AP를 깨워 데이터를 전달하지 않습니다. AP suspend 중에는 배치 제한이 전달을 강제하지 못하며 FIFO가 가득 차면 오래된 이벤트를 덮을 수 있습니다. 화면 상태는 AP 실행 상태와 별개입니다. 기존 10분 기록에서 실제 suspend 시각이나 FIFO 덮어쓰기 건수는 알 수 없으며, OS 센서 제한이나 단말 정책도 영향을 줄 수 있습니다. [AOSP 센서 배치 문서](https://source.android.com/docs/core/interaction/sensors/batching)

foreground service는 센서 작업의 수명과 사용자 알림을 관리합니다. CPU 유지 실험에서는 같은 5Hz 요청과 최대 5초 배치에 공식 `PARTIAL_WAKE_LOCK`을 추가합니다. 이 락은 화면을 켜지 않습니다. Android 정책이나 다른 센서 제한이 적용되면 락을 획득했어도 관측 공백이 생길 수 있습니다. [PowerManager API](https://developer.android.com/reference/android/os/PowerManager#PARTIAL_WAKE_LOCK) · [WakeLock 해제 안내](https://developer.android.com/develop/background-work/background-tasks/awake/wakelock/release)

## 0.5.0에서 사용하는 방법

- **독립 시험**은 워치의 센서 진단에서 10분 또는 15분을 선택합니다. **이 시험만 CPU 유지 (실험적)** 체크박스는 해당 시험에만 적용됩니다. 시험 중단이나 예약과 충돌하면 정리하고, 워치는 실제 예약을 우선 처리합니다.
- **실제 스마트 예약**의 기본값은 절전입니다. 화면을 끈 CPU 유지 시험의 관측률, 해제, 배터리 변화를 먼저 확인한 뒤 예약 설정에서 CPU 유지에 동의하고 새 예약을 만드세요. 설정은 예약에 포함되므로 이미 저장된 예약에는 다시 예약할 때 적용됩니다.
- 센서 등록 뒤 남은 시간만큼 non-reference-counted 타이머 락을 획득합니다. 독립 시험은 최대 선택한 10분 또는 15분, 실제 알람은 최대 스마트 범위 60분과 예열 15분입니다. 재시작하면 진행 중인 수집 범위에서만 남은 시간이 적용됩니다. 정시·조기 알람, 예약 변경·취소, 시험 중단, 시간 변경, 서비스 오류와 종료에서 해제합니다. 프로세스가 강제 종료되면 Android가 프로세스의 리소스를 정리합니다.
- 진단의 해제 시각은 정상 해제하거나 해제를 감지한 시각입니다. 유지 시간은 monotonic clock 기준입니다. timeout·OS 해제의 감지 시각은 실제 해제보다 늦을 수 있고, 갑작스러운 종료에서는 마지막 체크포인트 이후 유지 시간을 알 수 없습니다. `isHeld`는 앱 락 상태이며 실제 CPU suspend의 추적 로그와는 별개입니다.
- 배터리 잔량과 충전 상태는 Android 배터리 상태 보고값입니다. 잔량 차이는 참고값입니다. 화면 통계는 앱이 상태 변경을 관측한 시각을 기준으로 합니다. CPU가 멈춘 동안 화면 상태 콜백이 지연될 수 있고 앰비언트·미확인 상태는 순수 꺼짐과 별도로 집계합니다. 상태 경계를 걸친 5초 구간의 저장 관측률은 가능한 관측시간의 하한을 사용합니다.
- 충분한 자료가 없으면 기존 스마트 기상 조건에 따라 보류합니다. 80% 최소 관측률, 기준선, 조기 판정 임계값과 독립 정시 알람 경로는 기존과 같습니다.

## 실제 Watch7 비교 절차

아래 비교는 사용자 기기에 0.5.0을 설치한 뒤 진행합니다. 워치를 동일한 손목에 착용하고, 충전기를 분리하고, 절전 설정과 주변 조건을 동일하게 맞추세요. 화면 꺼짐 시험은 Always On Display와 손목으로 깨우기를 끄면 순수 꺼짐 구간을 확보하기 쉽습니다. 배터리 잔량은 주기적으로 바뀌는 정수이므로 가능한 한 같은 시작 잔량에서 각 조건을 반복하세요.

| 조건 | 진행 |
|---|---|
| A · 화면 켜짐 + 기본 | 10분 독립 시험에서 CPU 유지 체크를 끄고 화면을 켠 상태로 유지합니다. |
| B · 화면 꺼짐 + 기본 | 같은 10분 독립 시험에서 체크를 끄고 시작 직후 화면을 끕니다. 시험 종료까지 화면을 확인하지 않습니다. |
| C · 화면 꺼짐 + CPU 유지 | B와 같은 조건으로 CPU 유지 체크만 켭니다. 시험 종료 뒤 WakeLock 상태와 배터리를 확인합니다. |
| D · 화면 꺼짐 + CPU 유지 + 실제 알람 | C에서 수집 안정성과 종료 후 해제를 반복 확인한 다음 실험 설정을 켜고 새 스마트 알람을 예약합니다. 기본 30분 범위와 15분 예열이면 정시 45분 전부터 수집합니다. D가 길다면 A~C와 동일한 길이의 구간별 지표도 함께 보고, 배터리 차이는 실제 수집 길이를 적습니다. |

1. A~C 모두 실제 센서 등록, 시작·종료, 화면 상태별 시간, 이벤트·저장 관측률, 측정 시각 공백과 최대 수신 지연, DB 오류, 충전 여부를 기록합니다. 화면 꺼짐 시간이 짧았거나 앰비언트가 대부분이면 해당 결과를 화면 꺼짐의 비교 자료에서 제외합니다.
2. C의 공학적 목표는 화면 OFF의 이벤트·저장 관측률 각각 95% 이상, 최대 실측 공백 15초 이하, DB 오류 0건, 종료 후 WakeLock 해제 상태입니다. 보고서에서 정상 종료는 `RELEASED`로 확인합니다. 개발자 옵션으로 이미 ADB를 연결했다면 시험과 알람을 끝낸 뒤 `adb shell dumpsys power`의 활성 WakeLock 목록에 `dev.sleepalarm.app:MotionCapture`가 남아 있는지도 확인할 수 있습니다.
3. B와 C를 나란히 비교해 14.4%에 해당하는 낮은 관측률이 재현되는지, 락이 확보됐을 때 OFF에서 공백이 줄어드는지 확인합니다. 정상 종료 외에 `수집 시험만 종료`도 한 번 실행해 해제 상태를 확인합니다.
4. D에서 예열/판단 관측률과 실제 종료 시간을 확인합니다. 충분한 조기 근거가 없는 날의 정시 알람 소리·진동을 확인하고, 별도 확인에서 해제·다시 알림과 예약 취소를 점검합니다. 조기 알람이 난 경우 알람 요청 전까지의 수집만 비교합니다.
5. CPU 유지의 배터리 부담이 크거나 OFF에서 여전히 목표에 미달하면 기본 절전 설정으로 복귀합니다. 기기가 공개 wake-up 가속도 센서를 제공한다면 기존 FIFO 우선 경로가 대안입니다. 이 Watch7에서 확인된 센서는 non-wake-up입니다. Health Services의 심박·걸음 데이터로 가속도 공백을 채울 수 없으므로, 충분한 움직임 자료가 없을 때는 정시 알람을 사용합니다.

## 진단 화면과 전송

진단과 업데이트 Activity는 Android 테마의 색을 사용하는 밝은/어두운 테마를 각각 적용합니다. 휴대전화의 **최신 진단 가져오기**는 ID 없이 근처 워치에 요청합니다. **현재 선택한 진단 가져오기**는 열린 기록의 ID만 요청합니다. 요청 전송, 워치 수신 응답, 휴대전화 DB 저장을 따로 표시하며 워치에 기록이 없는 경우 사유를 반환합니다. 응답을 받지 못하면 연결과 양쪽 버전을 확인하고 버튼을 다시 누르세요. 재요청과 오래된 응답은 기록을 중복 저장하지 않습니다. 양쪽 앱을 0.5.0으로 업데이트하면 전송 확인을 사용할 수 있습니다. 워치와 휴대전화 사이의 근거리 메시지만 사용하며 원시 이벤트와 개인 기준선은 전송하지 않습니다.

## 검증 범위

자동 테스트는 모의 WakeLock의 획득·해제·timeout, 중복·오류·시험 중단, 화면 구간별 시간과 FIFO 공백, 예약 보호, 전송 응답·저장 및 시스템 테마 대비를 검사합니다. 실제 Watch7의 AP suspend, 수집률 개선, 배터리 소비 및 근거리 전송과 원형 화면은 위 절차로 확인해야 합니다.
